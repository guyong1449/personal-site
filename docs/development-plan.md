# GUYONG 后续功能开发计划

更新于 2026-08-30。本文件是后续开发的唯一状态源；`remaining-tasks.md` 只保留
最近一批的短清单。计划以“先保证内容不会丢、不会误发布，再增强展示体验”为顺序。

## 1. 已确认的当前基线

- 公共站点已有 `/`、`/notes`、`/gallery`、`/archive`、`/search`、
  `/account`、Note/Gallery 详情、RSS、Sitemap、robots 和 404 页面。
- Studio 仅监听 `127.0.0.1:4319`，生产环境没有 `/studio`，继续保持本机写作边界。
- `.local-content` 保存本机草稿、历史和草稿资产；`content/site` 是正式内容源；
  `content/public` 由 `site-builder` 生成，禁止手工修改。
- Studio 已有新建、导入、自动保存、历史版本、图片压缩、封面、定时发布、发布、
  下线和永久删除的界面与基础实现，但审计发现部分真实链路缺少测试并存在正确性问题。
- GitHub 已连接 Vercel，`main` 是生产分支；提交 `3318dbc` 已完成自动部署验证。
- 当前正式内容为 1 篇 Note，Gallery 仍为空；因此 Gallery、真实封面和下线 404
  尚未完成生产验收。
- 当前本机质量基线为 site-builder 6 项、Studio 24 项、Legacy publisher 9 项、
  Web 11 项，共 50 项测试通过。现有测试仍缺少完整浏览器 E2E 和线上冒烟覆盖。

## 2. 开发原则与产品边界

- Studio 是唯一主写作入口；Legacy Obsidian publisher 只保留迁移兼容，不继续扩展。
- 发布只处理当前内容及其资产，不允许宽范围暂存、自动提交整个工作区或隐式覆盖其他内容。
- 已发布内容改 slug 时，先下线、再改名、再发布；不在后台偷偷保留两个正式 URL。
- 原始 HTML 不进入内容契约；Note 使用 `content_type: note`，课程语义继续使用
  `course/*` 标签；Gallery 保持独立类型。
- 不引入数据库、远程 CMS、多人账号、外部搜索或统计，除非内容规模和使用场景证明需要。
- 每个代码批次完成后运行 `pnpm verify`；外部上线批次还必须核对同一提交的 CI、
  Vercel SHA 和线上路由。

## 3. P0：发布与数据安全

### P0-A：Studio 核心正确性（2026-08-30 已完成）

- [x] 修复 Markdown 导入接口与前端提交判断，并增加文件/粘贴、空内容、危险 HTML、
  slug 冲突和确认覆盖的 API 测试。
- [x] 允许从已发布快照建立本机草稿并继续编辑，完整保留置顶、定时、Gallery 分类/系列。
- [x] 修改 slug 后保存应返回新 slug；发布必须使用新 slug，保存失败必须立即停止发布。
- [x] 已上线内容不能从“永久删除草稿”接口绕过下线流程。
- [x] 自动保存不生成历史快照；手动保存和恢复继续保留版本。
- [x] 下线回草稿时完整保留 frontmatter；已有本机草稿时保留本机编辑并明确提示。
- [x] Cursor/计划任务自动同步改为“工作区干净时仅快进拉取”，不再自动 add/commit/push。

验收：新增 Studio API/流程测试通过；已发布内容可编辑并形成草稿；slug、删除、导入、
自动保存和下线行为符合上述规则；自动同步在脏工作区明确跳过；全仓 `pnpm verify` 通过。

### P0-B：事务恢复与 Git 提交隔离

- [ ] 发布/下线前保存操作清单和文件备份；在生成、检查、提交失败时自动回滚本地正式层，
  不留下“正式稿已删但流程失败”的半完成状态。
- [ ] 发布前检查受管内容路径是否已有改动；只暂存当前 slug、当前引用资产、三份生成索引和
  RSS，不允许把另一篇未完成内容带入提交。
- [ ] 资产同名但内容不同不得覆盖其他文章正在使用的文件；增加哈希或明确重命名策略。
- [ ] 为生成失败、测试失败、提交失败和推送失败增加故障注入测试，证明草稿和备份可恢复。

验收：测试仓库内准备两篇并行改动，只发布其中一篇时提交中不得出现另一篇；任一失败点
都能恢复到操作前文件状态，并给出明确的下一步修复指引。

### P0-C：真实生产闭环（外部状态批次）

- [ ] 准备一篇可下线的测试 Note 和一件带真实封面的测试 Gallery。
- [ ] 完成“Studio 发布 → Git 提交/推送 → GitHub Actions 通过 → Vercel Ready →
  线上页面与资产 200”的证据链。
- [ ] 对测试内容执行下线，确认第二次部署 Ready 后原详情 URL 为 404，草稿仍可恢复。
- [ ] 核对生产构建 SHA 与 GitHub 提交一致，不把“本机成功”当成“已经上线”。

验收：记录两个提交 SHA、两次 Vercel 部署和线上 200/404；整个过程不使用永久删除。
这一批会改变生产内容，执行前单独确定测试标题与上线窗口。

## 4. P1：Gallery、公开站体验与自动化测试

### P1-A：Gallery 分享和导航

- [ ] 为 Gallery 详情补齐 Open Graph/Twitter 元数据、封面图片和 `VisualArtwork`/
  `ImageObject` JSON-LD；无封面时使用稳定的 GUYONG fallback 卡片。
- [ ] Gallery 标签改为可筛选链接；分类和系列可进入对应列表筛选。
- [ ] 详情页增加同系列/同分类作品和前后作品导航，空结果不显示空容器。
- [ ] 列表封面 `sizes` 与 88px 桌面、移动端大图的真实断点一致，避免移动端取过小图片。

验收：带封面的 Gallery 分享链接显示正确标题、摘要和图片；tag/category/series URL
可复制、刷新和后退恢复；移动端图片清晰且没有明显布局跳动。

### P1-B：可访问性与阅读体验

- [ ] 修正浅色主题黄色标签、青色链接和弱化文字对比度；每组正文/边框 token 分别验证。
- [ ] Theme、移动菜单、返回顶部和标签控件的实际命中区至少 44×44px，视觉大小可保持紧凑。
- [ ] 桌面/移动导航增加 active 状态和 `aria-current`；移动菜单支持 Escape、外点关闭和焦点返回。
- [ ] 404 页面补 `main-content`、语义色 token 和两主题样式，保证 skip link 有有效目标。
- [ ] 每个详情页只保留一个 `h1`；正文基础字号移动端不低于 16px。
- [ ] 正文图片提供稳定尺寸/比例和响应式资源，避免 CLS；不可见的“返回顶部”不进入 Tab 顺序。
- [ ] 尊重 `prefers-reduced-motion`，焦点样式不能被移除。

验收：375/768/1024/1440、横屏、浅色/深色和键盘完成回归；普通文字对比度至少 4.5:1，
大文字和非文本控件至少 3:1；页面无水平溢出且主要交互可由键盘完成。

### P1-C：测试和质量门补全

- [ ] 增加 Studio API 集成测试和浏览器 E2E，覆盖新建、导入、编辑、自动保存、历史、
  资产、发布、下线、删除和定时发布。
- [ ] 增加公共路由、404、搜索、筛选、Metadata、RSS、Sitemap 和结构化数据测试。
- [ ] 把 `tsc --noEmit` 纳入 `pnpm verify`；依赖审计从仅报告改为有明确严重级别阈值。
- [ ] 增加不依赖生产写入的构建后 smoke：主页、Note/Gallery 列表、已知详情、资产、
  RSS 和 Sitemap。

验收：关键用户流程有失败前的回归用例；CI 对同一套质量门执行；新缺陷可以由单个测试
稳定复现，而不是只靠人工截图判断。

## 5. P2：内容契约、Studio 运维和 SEO

### P2-A：内容契约与资产可靠性

- [ ] 将非空正文、文件名与 slug 一致、日期格式、标签去重、cover/正文资产存在等校验
  下沉到 site-builder，保证手工内容也不能绕过契约。
- [ ] 上传接口在服务端校验真实图片类型、体积和像素边界；导入含外部相对图片时明确提示
  上传/绑定，不允许带着缺图引用发布。
- [ ] 增加孤立资产审计和安全清理预览；只有确认未被正式内容和本机草稿引用才可回收。

验收：坏日期、重复标签、slug 不一致、伪图片和缺失资产都在生成前失败，并指出具体文件。

### P2-B：定时发布、健康状态和桌面控制

- [ ] 定时任务显示“待发布、逾期、失败、最近一次尝试”；坏 `publish_at` 不再静默跳过。
- [ ] scheduler 单条失败不能打断后续任务或 Studio 服务；失败状态持久化并可手动重试。
- [ ] `/healthz` 扩展为进程、Git、内容生成、scheduler 和部署查询的分层状态。
- [ ] 桌面入口增加启动、停止、重启、PID 所有权、端口健康、日志入口和重复启动保护。
- [ ] 对 `.local-content` 的草稿、历史和资产建立可恢复备份，并完成一次临时目录恢复演练。

验收：故意制造坏定时任务和端口占用时，界面能说明失败层；重启不会误杀非本项目进程；
从备份可恢复一篇草稿及其资产。

### P2-C：搜索、日期与 SEO 一致性

- [ ] 元数据导出 `created`，Archive/RSS/Sitemap 在无 updated 时使用 created。
- [ ] 静态路由的 Sitemap 不再每次构建伪造新的 `lastModified`。
- [ ] 为首页/列表/Account/Archive 增加 canonical 和基础 OG/Twitter；Search 保持 noindex。
- [ ] 搜索文案与单个 CJK 查询行为一致；补空状态、清除操作、稳定高亮和 URL 状态。
- [ ] 若启用 Giscus，再实现初次加载和主题切换同步；未启用前不增加外部脚本。

验收：连续无内容变更构建的日期输出稳定；搜索 URL 可分享和后退；Metadata 与页面内容一致。

## 6. P3：长期运营（有需求再启用）

- [ ] 建立每月维护记录：依赖/安全、死链、图片引用、域名证书、CI、Vercel 和备份恢复。
- [ ] 真实内容量达到需要统计的程度后，再评估隐私友好的访问统计。
- [ ] Git 仓库因图片明显膨胀后，再迁移到对象存储并保留 `/assets/*` 兼容路径。
- [ ] 只有出现远程写作或多人协作需求后，才评估远程 CMS、账号和权限系统。

## 7. 推荐执行批次

1. **批次 1（当前）**：P0-A Studio 正确性 + 自动同步安全，完成全仓验证。
2. **批次 2**：P0-B 事务回滚 + 精确 Git 暂存 + 故障注入测试。
3. **批次 3**：P1-A Gallery 分享/导航 + P1-B 第一轮可访问性，使用测试 Gallery 本地验收。
4. **批次 4**：P1-C API/浏览器/路由测试和本地 smoke，收紧 CI。
5. **批次 5（需外部确认）**：P0-C 真实发布/下线闭环，并核对 GitHub/Vercel/线上证据。
6. **批次 6**：P2 内容契约、scheduler、健康状态和桌面控制。
7. **长期**：按真实内容量选择评论、统计、对象存储或远程协作能力。

## 8. 需要用户决定的事项

- P0-C 使用哪一篇测试 Note/Gallery，以及允许它们短暂出现在生产站的时间。
- 是否启用 Giscus；不开启时网站保持无评论脚本和无第三方请求。
- 本机草稿备份目标（另一块磁盘、私有 Git 或加密云盘）。
- 何时把测试内容替换为正式内容。功能开发不替用户编造正式作品。
